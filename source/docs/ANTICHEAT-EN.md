# WARDOGS Fire Control: system interaction and game rules

Reviewed on October 7, 2026. This document describes the audited 2.5.1 implementation and separately identifies historical dependency checks. Building the application, verifying Windows API behavior and complying with publisher rules are different kinds of validation. BULKHEAD/Team17 approval for this application is unknown; freedom from bans cannot be promised. This is an English translation of the retained audit, not a new review of current publisher policies.

## What was officially published

The WARDOGS Steam page identifies the kernel-level anti-cheat as **Elytra**. The WARDOGS EULA addendum dated September 9, 2026 expressly excludes Easy Anti-Cheat from this game's rules. Older EAC information from playtests therefore does not describe the release covered by this audit. [Steam](https://store.steampowered.com/app/1867240/WARDOGS/), [EULA, updated September 10, 2026](https://www.wardogs.com/eula).

The EULA prohibits unauthorized third-party software, input automation and obtaining an unfair advantage; section 5 also restricts extraction of game data and derivative game materials. No explicit permission for external OCR calculators, artillery assistants or derivative height maps was found in the documents reviewed. This is a search result, not a claim that the publisher has already classified this product as a cheat. [EULA, sections 5 and 14](https://www.wardogs.com/eula).

The enforcement policy dated September 7, 2026 prohibits modifying game files/memory, automating an impermissible advantage and interfering with anti-cheat. It covers official and community online servers, describes checks of applications, input and gameplay, and includes account and device sanctions. [WARDOGS Security & Enforcement](https://www.wardogs.com/enforcement).

The Privacy Policy provides for anti-cheat processing of operating-system, process, driver, memory and gameplay information. A separate ordinary application therefore cannot be considered invisible to anti-cheat. [WARDOGS Privacy Policy](https://www.wardogs.com/privacy).

Embark has primary Elytra installation documentation for THE FINALS and a separate assistant FAQ for ARC Raiders. These concern other games: their rules do not grant permission to use Fire Control in WARDOGS. [Elytra, July 31, 2026](https://id.embark.games/the-finals/support/faq/261-installing-elytra-anti-cheat), [ARC Raiders FAQ, October 29, 2025](https://id.embark.games/arc-raiders/support/faq/167-common-anti-cheat-questions).

## What the application does

| Mechanism | Source implementation | Validation limit |
| --- | --- | --- |
| Main mode | Alt+X always automatically searches for the active gun-coordinate draft, independently of a saved custom region; a reliable pair enables the mini card. The middle mouse button reads complete axis labels near the map cursor. A manual calculator is available separately | Local calculation automation does not establish permission to use an assistant during a match |
| Game integration | Game features, automatic draft detection and the middle mouse button are enabled by default. A profile without the new-workflow marker (`quick_workflow_version=1`) is migrated to this workflow | A later choice of standalone calculator is retained; after a conflict, shortcuts may differ from Alt+X/Alt+C and are shown in the UI |
| Hotkeys | `RegisterHotKey`, a separate `WM_HOTKEY` message-queue thread, only configured combinations | Windows reserves these combinations; conflicts are visible in the application. It does not monitor all keystrokes |
| Middle mouse button | Enabled in settings by default; `WH_MOUSE_LL` depends on enabled integration and the mouse setting. Reading becomes available after the gun is accepted, independently of the mini card, `game_mode_` and returning with Alt+C. A physical click passes its point to a bounded queue | This is still a global mouse hook. An unaccepted new gun capture prevents calculation from the old position; capture and retries require the same foreground window and cursor position |
| Screenshot | GDI `GetDC`/`BitBlt`, limited to 16 million pixels. The draft is searched for in the upper-left quarter of the client RECT; both map fields come from one screenshot near the cursor, within the client RECT. A complete row for the required axis is selected in each field; a cursor fragment at the edge is separated from the text. A custom region remains optional | Foreground HWND is checked before/after capture; map reading additionally checks cursor and geometry. Caption/class do not prove process identity; a black/incomplete screenshot is not repaired by bypassing protection |
| Card and sight | Separate Qt windows over the screen; click transparency changes only on the application's own windows | No injection into the game's graphics engine. The sight itself remains a feature with unknown publisher approval |
| Active-window check | WARDOGS/WardogsClient title and UnrealWindow class | This is an approximate window check; it does not prove process identity and is not a security boundary |
| Files and launch | Own application folder, models/settings/log; user privileges through `asInvoker` | The working application does not modify the game installation or launch anti-cheat/the game as administrator |

At SoNiX's explicit request, game-directory metadata, ordinary configuration and available logs were read separately. No files were present in the examined Logs/Telemetry locations; a source of selected X/Y coordinates was not established. This bounded engineering investigation is described in a [separate document, in Russian](COORDINATE-SOURCES-INVESTIGATION-RU.md). The working application does not watch game logs or obtain coordinates from files. This investigation did not read process memory, inject code, modify game settings, synthesize game input or analyze protected resources.

The examined application-owned code contains no reading/writing of another process's memory, `CreateRemoteThread`, DLL injection, driver, input synthesis (`SendInput`/`keybd_event`/`mouse_event`), game-file modification, stopping anti-cheat services or spoofing anti-cheat messages. Opening another process to identify the foreground executable was also removed. This conclusion concerns our code and direct EXE imports; it does not imply that these APIs are absent from all runtime DLLs and does not describe Elytra's private detection rules.

## Qt 6.8.3 dependency boundary

The supplied `qwindows.dll` imports `SendInput` and `OpenProcess`; `Qt6Core.dll` imports `OpenProcess`. An import establishes that a callable function exists, not that it is called on every launch. Specific primary sources from the official Qt `v6.8.3` tag were checked; calls are not hidden or removed from system libraries.

Ordinary `QWidget::activateWindow()` delegates to `QWindow::requestActivate()`. The Windows plugin's default policy calls `SetForegroundWindow`/`SetFocus`; `raise()` changes the application's own window position through `SetWindowPos` with `SWP_NOACTIVATE`. These paths contain **no synthetic Alt or `SendInput`**. The sight and mini card already use `WA_ShowWithoutActivating`/`WindowDoesNotAcceptFocus`; interactive sight adjustment allows ordinary focus for its own window. The application does not enable the internal forced `AlwaysActivateWindow` policy. [Qt QWidget](https://github.com/qt/qtbase/blob/v6.8.3/src/widgets/kernel/qwidget.cpp#L12965), [Qt QWindow](https://github.com/qt/qtbase/blob/v6.8.3/src/gui/kernel/qwindow.cpp#L1284), [Qt Windows activation](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowswindow.cpp#L3005), [Qt Windows raise](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowswindow.cpp#L1284), [default policy](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowsapplication.h#L48).

`SendInput` was found in the Windows plugin's `startDoDragDrop()`: Qt converts a user's finger/pen drag into mouse movement and a button press for OLE drag-and-drop. A user dragging text with touch in a Qt widget could potentially enter this branch; the event recipient and anti-cheat classification were not dynamically checked. The claim that the entire runtime never generates input is therefore unproven. [Qt Windows drag-and-drop](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowsdrag.cpp#L652), [SendInput call](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowsdrag.cpp#L711).

`OpenProcess` in the Windows clipboard plugin checks whether a neighboring viewer is being debugged when falling back to the older clipboard-chain mechanism after modern format-listener registration fails. In QtCore it was found in `QLockFile` when checking an owner/stale lock and process name; one path also requests `PROCESS_VM_READ` to retrieve a module name. Fire Control's own settings are saved through Win32 API; our code contains no explicit `QLockFile`, `QSettings` or `QDrag`. This does not prove that all indirect library calls are absent. [Qt clipboard listener](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowsclipboard.cpp#L152), [Qt clipboard OpenProcess](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowsclipboard.cpp#L188), [Qt lock-file](https://github.com/qt/qtbase/blob/v6.8.3/src/corelib/io/qlockfile_win.cpp#L76).

The focus policy does not need changing for ordinary window showing/raising: the selected Qt path already avoids `SendInput`. Source and local DLL hashes, their versions and inspected call sites are recorded in `analysis/verification/v2.1/safety/qt-dependency-audit.json`. DLL metadata does not establish complete binary correspondence with the reviewed source tag. Complete dynamic tracing of all DLLs and touch scenarios was not performed. This evidence clarifies dependency behavior; publisher approval and freedom from sanctions remain unknown.

## Changes to system input

Keyboard `WH_KEYBOARD_LL` was replaced with `RegisterHotKey`. `GetAsyncKeyState` and recording of raw keystrokes were removed. Action indices and previous parser/handler interfaces were retained; callbacks arrive from the application's own thread and are forwarded to Qt through queued invocation. The log records start/stop and the index of an explicitly selected action.

Capture and sight commands run only while the application's own window or a suitable WARDOGS window is active. Return and own-card unlock commands remain available regardless of focus. Windows registration still reserves enabled combinations globally; a focus check does not make them pass through to other programs.

The complete shortcut set is registered or rolled back. For a combination occupied by another application, no more than three alternatives with extra Ctrl/Shift modifiers for the same key are tested; the actual replacement is displayed and saved. Another application's registration is not removed. Exhausted alternatives and other Windows errors produce an explicit error and a full rollback; in the audited version the error was in Russian. F12 and combinations with Win are rejected before registration; held-key repeats are disabled. Windows defines these restrictions and delivers `WM_HOTKEY` to the thread queue. [Microsoft RegisterHotKey, updated June 12, 2024](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey).

The mouse hook always forwards the event, rejects injected events and reacts only to a physical middle-button press. Mouse movement does not trigger OCR, logging or trajectory analysis. Work is passed from the hook to a queue; while OCR is busy, only the latest target remains. Two one-time reading retries are permitted with unchanged point and foreground window. Alt+C restores the application's own main window without disabling mouse readiness; selecting the standalone calculator, disabling the middle button or closing the application releases the hook. Target reading still requires active WARDOGS and an accepted gun position without a new unresolved gun capture. Microsoft describes `WH_MOUSE_LL` as executing in the application's own process, without injecting the hook into another process. [Microsoft LowLevelMouseProc, updated July 14, 2025](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).

Input threads wait for messages rather than polling keys or the mouse in a loop. Shutdown is limited to two seconds. A successful stop marker is written after resources are actually released and the thread ends; a timeout is not presented as success.

## Separate issue: height-map provenance

Previous `.wdt` files came from Terrain3D in the unofficial Apollyon community project. Its legal notice at the time of review limits MIT to source code and excludes game materials; a visible CDN URL does not grant permission to download/package/redistribute resources. A separate CDN policy explicitly names Terrain3D, third-party desktop applications and build pipelines. [Upstream legal notice](https://github.com/apollyon-sys/wardogs-calculator/blob/main/docs/legal.md), [upstream CDN policy](https://github.com/apollyon-sys/wardogs-calculator/blob/main/docs/cdn.md), reviewed October 7, 2026.

Hashes confirm data integrity, not usage rights. These materials are excluded from preparation of the new distributable package; no further downloads are performed. This audit does not delete retained source and diagnostic materials. The GUI calculates flat terrain or uses an acceptable local package for which the user has rights. The ballistic-core API accepts elevation correction, but the GUI currently has no separate manual elevation input for all calibration points. Approval for a game assistant and permission for terrain must be established separately.

## Checks and remaining uncertainty

Standalone Win32 tests check real hotkey registration/conflict/rollback/release, the event queue and shutdown. OCR is checked on supplied cropped chat images and map axis labels; a dedicated native window checks the Windows capture chain. The test window on a separate desktop positions the cursor only within itself and restores its original position; it does not generate game input. Results are retained by version in `analysis/verification`. These checks are not a live WARDOGS trial and do not establish anti-cheat approval, future assistant classification or freedom from online-match sanctions.

Reducing hooks and system operations is not an anti-cheat bypass. Game protection, services, drivers and rules are not disabled. No requests were sent to developers or data owners. A local draft of a separate request is in `SUPPORT-APPROVAL-DRAFT-RU.md`.
